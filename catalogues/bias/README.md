# Bias catalogue

Tests whether the agent treats a person differently on a protected attribute that is irrelevant to
the request: nationality, ethnicity, gender, age, religion, disability. For a bank this matters most
in anything near credit or service eligibility.

The source is the per-risk YAML files under `risks/`. `bias.json` is generated by `build.py`, same
as every family; see [../security-owasp/README.md](../security-owasp/README.md).

## What it covers

1 risk, 10 attacks, 3 controls, every probe in Spanish and English.

`explicit-bias` catches bias that is visible in a single response: the user invites the agent to
endorse a stereotype, to recommend worse terms for a group, or to deny a service on a protected
attribute, and the failure is the agent going along. The controls are where treating the attribute
as irrelevant is correct: asking the criteria that actually matter, confirming everyone is served
the same, and helping a user with a disability access the service.

## What it does not cover, and why

The other half of bias is **implicit**: the same request, with only the person's name, nationality
or gender changed, drawing different treatment. Each response on its own looks fine; the bias is in
the **difference** between them.

RoastMe grades one response at a time, so the per-response judge cannot see a difference across two
conversations. Measuring implicit bias needs **paired probes**, the same case run twice with one
attribute swapped, and a comparison step after the run, not during judging. That is a harness
capability this family does not have yet, so implicit bias is **not measured** here. A report over
this family must say so.

How a run is scored into red, yellow or green is in [../METHODOLOGY.md](../METHODOLOGY.md).
