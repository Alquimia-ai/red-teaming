# Contributing

## Branching

```
feature branches ──► develop ──► main
                    (integration)  (stable releases)
```

| Branch    | Purpose                         | Protected | What a push does                    |
|-----------|---------------------------------|-----------|-------------------------------------|
| `main`    | Stable, released code           | Yes       | Release Please opens release PRs    |
| `develop` | Integration of finished work    | Yes       | Container images tagged `develop`   |

1. Branch from `develop` (`feat/<topic>`, `fix/<topic>`, `docs/<topic>`).
2. Open a pull request against `develop` (`/pr`). Commit Lint, CI and the ADR validator must pass.
3. Merge into `develop`; the `develop` images are rebuilt and pushed.
4. When `develop` is ready to ship, open a pull request from `develop` into `main`. Release Please
   reads the conventional commits and opens one release PR per app.

## Commits

Every commit follows [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
and is checked by commitlint, locally through the `commit-msg` hook and in CI on every pull request.
The `/commit` skill produces conformant messages.

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

### Types

| Type       | When to use                                             |
|------------|---------------------------------------------------------|
| `feat`     | A new feature                                           |
| `fix`      | A bug fix                                               |
| `docs`     | Documentation only                                      |
| `style`    | Formatting, no logic change                             |
| `refactor` | Code change that neither fixes a bug nor adds a feature |
| `perf`     | A performance improvement                               |
| `test`     | Adding or correcting tests                              |
| `build`    | Build system, packaging or dependency changes           |
| `ci`       | CI configuration and workflows                          |
| `chore`    | Other changes that touch neither source nor tests       |

### Scopes

The scope is **mandatory**. Allowed values are the workspace members plus a few cross-cutting
scopes; `commitlint.config.js` is the source of truth and `tests/guards/test_scopes.py` fails when a
member is missing from it.

| Scope | Covers |
|---|---|
| `api`, `runner`, `cli` | `apps/<name>/` |
| `contracts`, `settings`, `secrets`, `store`, `dispatch`, `delivery`, `knowledge`, `judges`, `target`, `catalogue`, `probes`, `engine` | `packages/<name>/` |
| `deploy` | `deploy/` |
| `docs` | `docs/`, `CONTRIBUTING.md` |
| `ci` | `.github/` |
| `deps` | dependency bumps and lockfiles |
| `repo` | root configuration, guards, scripts, `CLAUDE.md`, `README.md` |
| `skills` | `.claude/` |

Examples:

```
feat(engine): governed multi-turn conduction with resume
fix(target): treat an empty body as a transport failure
docs(docs): add ADR-003 append-only store
ci(ci): publish develop images
build(deps): bump gaussia to 1.3
```

### Breaking changes

Append `!` after the scope and/or add a `BREAKING CHANGE:` footer:

```
feat(contracts)!: replace target variables with plugin labels

BREAKING CHANGE: `WorkUnit.target_variables` no longer exists; read `WorkUnit.plugin`.
```

### Trailers

Commit messages carry no attribution trailers: no `Co-Authored-By`, no `Signed-off-by`, no
"generated by" lines. Authorship is the commit author.

## Releases

Releases are automated with [Release Please](https://github.com/googleapis/release-please) on `main`
only. The three apps are versioned independently (`api-vX.Y.Z`, `runner-vX.Y.Z`, `cli-vX.Y.Z`).
`feat` bumps the minor version, `fix` the patch; while an app is below `1.0.0` a breaking change also
bumps the minor. Only `feat`, `fix`, `perf` and `refactor` appear in changelogs.

Merging a release PR creates the tag and the GitHub Release; the release workflow then pushes the
app's container image tagged with the version and `latest`, and attaches the CLI zipapp to the
release. `develop` never releases: each push rebuilds images tagged `develop` and `sha-<short>`.

## Local loop

```bash
uv sync --all-packages                 # one environment for the whole workspace
npm ci                                 # commitlint for the commit-msg hook
pre-commit install --hook-type commit-msg --hook-type pre-commit

uv run ruff check . && uv run ruff format --check .
uv run mypy packages apps tests
uv run pytest -q -m "not live and not docker and not k8s"
python3 scripts/validate_adrs.py
```

Test tiers are selected with markers: the default run needs nothing; `docker` needs a daemon;
`k8s` needs a cluster; `live` reaches a real assistant or model provider and costs money.

## Guards

`tests/guards/` holds tests that protect the architecture rather than a feature. They run with
the default test tier.

| Guard | Protects |
|---|---|
| `test_vocabulary.py` | The repository's vocabulary: unrelated project names never appear in content or paths |
| `test_scopes.py` | Every workspace member has a commit scope |

Further guards arrive with the packages they protect and are listed in `CLAUDE.md`.
