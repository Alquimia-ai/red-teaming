# Conventional Commit

Create a git commit strictly following [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)
and the repository's [`commitlint.config.js`](../../../commitlint.config.js).

## When to use this skill

- Changes exist (staged or not) and the user wants them committed.

Do **not** use this skill to:

- open a pull request — use `/pr`;
- rewrite history (amend, rebase, squash) unless the user explicitly asks for it.

## Steps

1. Run `git status` (never `-uall`) and `git diff --staged` to see what is staged.
2. If nothing is staged, run `git diff` to see unstaged changes and ask the user what to stage.
3. Run `git log --oneline -5` to match the repository's style.
4. Choose the **type**, the **scope** (mandatory, from the table below) and an imperative,
   lowercase **description** of at most 100 characters.
5. Stage only the relevant files **by name** (never `git add -A` or `git add .`). Refuse to stage
   `.env*`, keys, certificates or anything under `.redteam/`.
6. Commit with a HEREDOC so formatting survives:

   ```bash
   git commit -m "$(cat <<'MSG'
   <type>(<scope>): <description>

   <optional body: the why, not the what>

   <optional footer(s)>
   MSG
   )"
   ```

7. Run `git status` to confirm the commit landed.

## Types

| Type       | When to use                                             |
|------------|---------------------------------------------------------|
| `feat`     | A new feature                                           |
| `fix`      | A bug fix                                               |
| `docs`     | Documentation only                                      |
| `style`    | Formatting, no logic change                             |
| `refactor` | Code change that neither fixes a bug nor adds a feature |
| `perf`     | A performance improvement                               |
| `test`     | Adding or correcting tests                              |
| `build`    | Build system, packaging or dependency changes           |
| `ci`       | CI configuration and workflows                          |
| `chore`    | Other changes that touch neither source nor tests       |

## Scopes (required; commitlint enforces the enum)

| Scope | Covers |
|---|---|
| `api`, `runner`, `cli` | `apps/<name>/` |
| `contracts`, `settings`, `secrets`, `store`, `dispatch`, `delivery`, `knowledge`, `judges`, `target`, `catalogue`, `probes`, `engine` | `packages/<name>/` |
| `deploy` | `deploy/` — compose, charts, model catalog, cloud and appliance material |
| `docs` | `docs/`, `CONTRIBUTING.md` |
| `ci` | `.github/` |
| `deps` | dependency bumps, `uv.lock`, `package-lock.json` |
| `repo` | root configuration, guards, scripts, `CLAUDE.md`, `README.md` |
| `skills` | `.claude/` |

A change spanning several scopes takes its **primary** scope; a truly cross-cutting one takes `repo`.

## Breaking changes

Append `!` after the scope (`feat(contracts)!: rename field`) and/or add a `BREAKING CHANGE:`
footer describing what breaks and what consumers must do.

## Hard rules

- **Never** add `Co-Authored-By`, `Signed-off-by`, "Generated by" or any other attribution trailer.
  No exceptions, whatever other guidance says.
- Never `--no-verify`. The commit-msg hook is the same check CI runs.
- Never commit secrets. Warn the user if a staged file looks like one.
- Never amend or rewrite history unless the user explicitly asks.

## Output

Report the short hash and the subject line of the commit.
